## 二、本輪順帶修復的兩個核心 bug

這兩人 bug 都不是理論預測,而是**實際跑 `demo`/`lsp` 時撞見並定位**的 —— 正是 #9/#10 的價值。

### Bug 1:`clone_subtree` 自環 → `reparse` 樹畸形 → `sexp`/`unparse` 爆棧(SIGKILL/OOM)

- **症狀**:`cargo run --bin demo` 在逐鍵模擬中途被 SIGKILL(exit 137);最終內容單獨 `parse`
  無恙(reused=3 total=94),但 `out.tree.sexp()` 深遞歸爆棧(exit 134)。
- **根因**:`src/parse.rs::clone_subtree` 的 DFS 階段用 `nodes.len()` 當新 id —— 該階段尚未 push
  任何節點,`nodes.len()` 恆為常數 ⇒ 所有克隆節點分到**同一個** id ⇒ `children` 全指向根(自環)。
- **修復**:改用遞增計數器 `next_id`。
- **為什麼既有測試沒抓到**:`test_reuse_data_consistency` 只檢查**節點計數**(`out.total` 與新樹),
  不檢查結構;自環下的 count 仍對。新回歸 `test_reparse_tree_structurally_sound` 鎖死結構健全
  (`sexp` ≡ `parse(new_src).sexp`、無環、children 全部有效)。

### Bug 2:`uri_of` 二次索引 `textDocument` → LSP 永不發佈診斷

- **症狀**:LSP 對 `initialize`/`shutdown` 有回應,但 `didOpen` 後從不發 `publishDiagnostics`。
- **根因**:`src/lsp.rs::uri_of` 先 `params.get(doc)`(doc="textDocument",已回傳該文件物件),
  又對其 `.get("textDocument")` —— 物件內無此鍵 ⇒ 恆失敗 ⇒ `uri_of` 永遠 `None`。
- **修復**:只取一次 `uri`。
- **回歸**:`tests/editor_tooling.rs::test_lsp_publishes_diagnostics_for_open` 斷言壞文檔
  必須發 ≥1 條診斷(此斷言在修復前失敗)。
